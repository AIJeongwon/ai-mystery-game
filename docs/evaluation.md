# 평가 기준과 확인 방법

| 항목 | 평가 기준 | 제출할 때 확인할 기록 |
|---|---|---|
| Git | 브랜치를 계층적으로 관리하고 PR로 소스 코드를 업데이트합니다. | 기능 브랜치의 분기·병합 그래프, 변경 내용과 검토 내역이 남은 PR |
| 컨테이너 | Docker Compose로 컨테이너 3종 이상을 사용하거나, Kubernetes로 컨테이너 3종 이상과 Pod 2개 이상을 구성합니다. 컨테이너 간 통신과 볼륨을 사용합니다. | 구성 파일, 서비스 간 요청 결과, 볼륨을 유지한 채 컨테이너를 재생성한 뒤 같은 데이터를 조회한 결과 |
| 추가 오픈소스 | 수업에서 사용한 도구 외에 오픈소스를 1개 이상 실제 기능에 활용합니다. 프로그래밍 언어와 오픈소스 DB는 이 항목에서 제외합니다. | 사용한 도구와 버전, 라이선스, 게임에서 동작하는 위치 |
| GitHub Actions | 서로 다른 검사를 수행하는 워크플로를 5개 이상 운영합니다. | 워크플로 파일, 각 검사의 목적, 실행 결과 링크 |

브랜치 운영 방식은 [협업 규칙](../CONTRIBUTING.md)을 따릅니다. 기술 후보와 구현 계획은 실제 실행 기록과 구분해 적습니다. 포크 PR의 자동 검사는 개인 키 없이 실행할 수 있게 구성합니다.

## 외부 API를 사용하는 구성안

웹 서버, 게임 서버, DB를 서로 다른 Docker Compose 서비스로 실행하는 방안을 제안합니다. 플레이어의 요청은 웹 서버를 거쳐 게임 서버로 전달됩니다. 게임 서버는 진행 기록을 DB에 저장·조회하고, 인터뷰와 엔딩 회고에 필요한 응답은 외부 LLM API에 요청합니다. 컨테이너 수는 Compose에서 실행하는 세 종류로 계산합니다.

| 확인할 항목 | 검증 계획 |
|---|---|
| 컨테이너 통신과 볼륨 | 웹 서버를 통해 게임 서버에 요청하고 진행 기록을 DB에 저장합니다. DB 볼륨을 유지한 채 DB 컨테이너를 재생성한 뒤 같은 기록을 조회합니다. |
| 자동 검사와 실제 응답 | 포크 PR에서는 개인 키 없이 고정 응답으로 검사합니다. 게임 서버 연동 후 실제 API로 인터뷰와 엔딩 회고의 품질·응답 시간을 별도로 확인합니다. |
| 추가 오픈소스 | 수업에서 사용하지 않은 별도 오픈소스를 게임 기능에 적용하고 사용 위치와 라이선스를 기록합니다. 외부 LLM API 호출은 이 항목의 실적에서 제외합니다. |
